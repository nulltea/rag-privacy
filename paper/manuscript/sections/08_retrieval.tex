The RAG retrieval and storage layer is a confidentiality problem distinct from inference: the
threat is not \emph{what} the server computes but \emph{which} records a query touches and what
the encrypted index reveals at rest, so its primitives are access-hiding and data-hiding rather
than compute-hiding, and they compose with the compute-hiding inference layer (\cref{sec:crypto})
but are costed and attacked separately. We organize the layer by the retrieval \emph{functions} that a confidential RAG stack performs in sequence, and report on the schemes that make them confidential.

First, \emph{scoring similarity over a stored index}
(\cref{ssec:retr-similarity}), made confidential either by distance-comparison-preserving
encryption (DCPE), which encrypts the vectors so a standard index still ranks the ciphertext, or
by homomorphic scoring, which keeps the similarity values themselves encrypted. Second,
\emph{hiding which record a query fetches} (\cref{ssec:retr-access}), secured by private
information retrieval (PIR) or oblivious RAM (ORAM). A Graph/LightRAG stack~\citep{guo_lightrag}
adds three more. \emph{Constructing the knowledge graph} confidentially (\cref{ssec:retr-kgconstruct})
has no dedicated primitive: it reduces to confidential inference over the extraction step
(\cref{sec:crypto}--\cref{sec:hybrid}) plus encrypted storage. \emph{Expanding adjacency and
fanning out to source chunks} (\cref{ssec:retr-adjacency}) uses structured and searchable
encryption with encrypted multi-maps (SSE/EMM), layered over ORAM where the access pattern must
hide as well. And \emph{running the whole traversal end-to-end} (\cref{ssec:retr-e2e}) relies on a
trusted execution environment (TEE) or heuristic anonymization. Several schemes serve more than
one function; we place each where its contribution is distinctive and cross-reference the rest.

By the paper's deployment-readiness lens, these schemes are performant in isolation but rarely
self-sufficient: the no-trusted-hardware designs cover retrieval and storage, not generation, and
shift the embedding, re-ranking, and traversal steps to the client (\cref{sec:synthesis}).

\subsection{Confidential Similarity over a Hidden Index}
\label{ssec:retr-similarity}
Dense retrieval ranks the corpus by similarity to a query embedding. The first confidentiality
function is to compute that ranking without revealing the stored vectors or the query, because an
embedding is a lossy but invertible encoding of its text, readable by inversion models such as
Vec2Text~\citep{vec2text}: the query embedding discloses the user's question and the stored
vectors disclose the corpus (\cref{tab:retr-perf}). Two families make the similarity computable
over hidden vectors and trade differently between leakage and cost.

\paragraph{Distance-comparison-preserving encryption (DCPE).}
The most direct approach encrypts each vector with a symmetric transform
($c = s\,e + \lambda$, the same dimension as the plaintext embedding, so the ciphertext imposes
${\approx}1\times$ storage) that preserves distance \emph{comparisons}, so a standard similarity
index ranks the ciphertext at near-plaintext speed with no interaction and no homomorphic
operations (CAPRISE encrypts 2339\,vectors/s). This is the drop-in confidential dense index. The
two schemes differ in \emph{which} comparisons survive. SAP~\citep{fuchsbauer_sap} preserves
\emph{all} pairwise comparisons, including those among database vectors, which leaks the corpus's
relational structure. CAPRISE~\citep{ye_caprise} is \emph{conditional}: asymmetric noise on query
versus database encryptions preserves only query-to-document comparisons while obfuscating
inter-document ones, and a differential-privacy perturbation of the query blocks inversion,
closing the structural leak SAP leaves open. Either way the price is exactness and a quantified
comparison leak, examined in \cref{ssec:retr-limits}.

\paragraph{Homomorphic and secret-shared scoring.}
Where any comparison leak is unacceptable, a second family keeps the similarity \emph{values}
themselves encrypted: the server scores the encrypted query against encrypted database vectors so
neither the scores nor their order ever appear in the clear. TRSE pairs two-round searchable
encryption with homomorphic top-$k$ scoring; RAGtime-PIANO layers CKKS scoring over a lattice-PIR
backend; and p\textsuperscript{2}RAG computes the scores under two-server secret sharing.
RemoteRAG is two-stage: it first coarse-retrieves $k'$ candidates against a DistanceDP-perturbed
embedding (the server sees only the noised query), then computes \emph{exact} cosine-similarity
top-$k$ over those $k'$ with the true query under partially-homomorphic encryption (PHE), reaching
$0.67$\,s at $100\%$ recall for a small privacy budget; the user decrypts and sorts the returned
distances locally, with optional oblivious transfer for the final fetch. The shared cost is the
homomorphic arithmetic per candidate, so these schemes prune the candidate set by DP or clustering
before scoring; the shared benefit is that one machinery hides both the query embedding and the
at-rest vectors. The query-side differential privacy in RemoteRAG and CAPRISE is the cheaper
relaxation: it protects the query embedding alone, accepting a bounded distortion in place of a
cryptographic guarantee.

\subsection{Access-Pattern Hiding}
\label{ssec:retr-access}
A scheme can hide the vectors and still leak \emph{which} records a query touches or returns; over
repeated queries this access pattern alone supports database-reconstruction
attacks~\citep{kellaris2016leakage}. The second dense function closes that channel: the server
returns the matching records without learning which were touched. Panther and PIR-RAG retrieve
through private information retrieval (single- or multi-server, classical or lattice-based), so the
fetch reveals nothing about which record matched. The cost driver is the obliviousness itself:
PIR keeps communication sublinear but forces a server-side linear scan, which is why these run in
seconds at million-scale rather than milliseconds (Panther $18$\,s at $10$M, PIR-RAG $16.8$\,s at
$5$K).

Compass and Pacmann reach the same goal over a graph-based ANN index (HNSW or NSG), the index most
accurate for high-dimensional embeddings. Despite the ``graph'' in their construction they are
dense-retrieval schemes: each vertex is a database vector, not a knowledge-graph entity. Pacmann
runs the iterative ANN traversal on the client and privately fetches each hop's subgraph by
batched PIR over a public database, reaching $90\%$ of non-private ANN quality and $-22\%$ latency
at $100$M vectors. Compass wraps an encrypted HNSW index in client-side Ring-ORAM to defend even a
\emph{malicious} server, leaving only the operation type visible, at sub-second LAN latency. The
TEE baseline Opal (\cref{ssec:retr-e2e}) reaches the same access-hiding goal with hardware trust
instead of client-side cryptography.

\begin{keyinsight}
At Tier~1 (no trusted hardware), access-pattern hiding is not free; its cost moves to the
client. Compass keeps the ORAM position map and runs a multi-round controller ($\approx$500\,MB of
client state at corpus scale, against a $27$--$75\times$ larger full client-side index), and
Pacmann streams the entire database to preprocess it. The TEE alternative (Opal) hides the same
access pattern with only a key and a counter on the client, but pays for it in a confidential
GPU. The design variable is not whether obliviousness costs, but \emph{where} it is paid: on the
client or on trusted hardware.
\end{keyinsight}

\subsection{Confidential Knowledge-Graph Construction}
\label{ssec:retr-kgconstruct}
Graph/LightRAG retrieval presupposes a knowledge graph: an LLM extracts entities and relations
from the corpus into a graph index, with key-value profiles and source-chunk pointers, before any
query runs~\citep{guo_lightrag}. Constructing that index confidentially on untrusted
infrastructure is the one retrieval function no surveyed scheme provides. It decomposes into two
parts covered elsewhere: the extraction is itself an LLM inference over sensitive text, to which
the inference families of \cref{sec:crypto}--\cref{sec:hybrid} apply, and the resulting graph must
be stored encrypted (\cref{ssec:retr-adjacency}); but no design composes them into an outsourced
confidential construction. The RAG-native systems sidestep the function by keeping construction
inside the trust boundary: PrivGemo's local Hand holds the raw graph and builds a question-specific
view on-device, Opal ingests inside its TEE enclave, and ARoG assumes a pre-built graph it only
anonymizes. Confidential construction from text on an untrusted server remains open
(\cref{sec:synthesis}).

\subsection{Adjacency Expansion and Graph Storage}
\label{ssec:retr-adjacency}
Once the graph exists, LightRAG retrieval matches query keywords to entity and relation nodes (a
dense ANN over entity embeddings, served by the schemes of
\cref{ssec:retr-similarity}--\cref{ssec:retr-access}), then expands one hop to neighboring nodes
and edges and fans each entity out to its source chunks. The expansion and fan-out are the
graph-specific function, and they leak along structural channels that dense primitives do not
address. The \emph{node access pattern} (which entity a query resolves to) identifies the subject
directly. The \emph{adjacency volume} (how many neighbours a one-hop expansion returns) is a degree
signature, and a degree sequence re-identifies nodes against a public graph even under encryption.
The \texttt{source\_id} \emph{fan-out} (which chunks an entity maps to) links a query to specific
source documents.

These channels are closed by general-purpose encrypted-graph-database machinery applied to the RAG
adjacency step, not by RAG-designed schemes. XorMM and FLASH encrypt the adjacency and keyword
multi-maps and pad result-set size so the query-result \emph{volume} does not leak (adjacency and
\texttt{source\_id} fan-out alike), at a storage overhead from near-optimal (FLASH, within a small
constant of the volume-hiding lower bound) to ${\approx}1.2$--$2.5\times$ (XorMM); FLASH's
conjunctive variant adds a keyword-pair access pattern of its own, and XorMM's verifiable variant
VXorMM detects a malicious server returning forged or incomplete postings by authenticating the
response with aggregate MACs, at twice the storage and a verification cost linear in the returned
volume. PeGraph combines searchable encryption with secret sharing for ranked adjacency queries
over million-entity graphs in under a second; GORAM is the heavier-trust 3PC fallback for
billion-edge federated graphs ($58$\,ms to $36$\,s, initialization under $3$ minutes); and
H$_2$O$_2$RAM supplies a doubly-oblivious RAM substrate inside a TEE beneath such a store. What
remains across all of them is the search/query-equality pattern, not the content, closed only by
layering ORAM (\cref{ssec:retr-access}) or rotating keys per session.

\subsection{End-to-End Confidential KG-RAG}
\label{ssec:retr-e2e}
The only systems that run the whole graph-RAG pipeline confidentially are RAG-native, and they
rest on trusted hardware or heuristic anonymization rather than provable retrieval cryptography.
Opal layers a knowledge-graph filter, embedding lookup, ANN top-$n$, and data fetch inside a TEE,
every step made access-pattern-oblivious through Ring-ORAM, at $2.32$\,s per query
($1.57\times$ over a non-oblivious baseline) and $+13$\,pp ANN quality. Where even a TEE is
unavailable, anonymization attacks the leakage channels directly at no cryptographic cost. ARoG
replaces entity names with machine identifiers so a remote LLM reasons over de-identified triples,
reaching state-of-the-art KGQA at some utility loss. PrivGemo~\citep{tan_privgemo} extends this
with structural de-uniqueness: a local Hand explores the raw graph and ships the remote Brain only
a pruned, HMAC-pseudonymized subgraph view, removing the uniquely-identifying topology that the
degree and adjacency channels would otherwise leak (${\approx}70\%$ node reduction, e.g.\ a
${>}2.4$M-node ComplexWebQuestions (CWQ) subgraph to ${\approx}732$K), with a fresh session key so
the views do not link across sessions. These preserve answer quality but are quality-preserving
\emph{obfuscation} with unquantified residual leakage (the anonymization lineage of
\cref{sec:hybrid}), not a provable-confidentiality guarantee. No surveyed design delivers an
end-to-end confidential graph-RAG pipeline with a cryptographic guarantee, which is why the
confidential-RAG frontier sits at the retrieval functions above rather than at an integrated graph
stack (\cref{sec:synthesis}).

\subsection{Limitations and Known Attacks}
\label{ssec:retr-limits}

The retrieval schemes trade exactness or residual leakage for their speed, and the attacks consume
that leakage per function. \cref{tab:retr-threat} places every scheme on the security axes of
\cref{sec:threat-axes}, and \cref{tab:retr-attacks} lists the known attacks.

\paragraph{Similarity over a hidden index.}
The distance-comparison-preserving schemes (SAP/DCPE, CAPRISE) preserve distance
\emph{comparisons} on ciphertext by construction. That is precisely the leak. The
property-preserving-encryption family is invertible from ciphertext plus an auxiliary data
distribution~\citep{naveed_ppe_2015}, and the embeddings recovered this way are readable as text by
inversion models such as Vec2Text~\citep{vec2text}; SAP additionally preserves inter-document
comparisons, exposing the corpus's relational structure. CAPRISE is the co-designed defense: it
makes the comparisons \emph{conditional} (obfuscating inter-document distances) and perturbs the
query under differential privacy. Distance-revealing search also exposes $k$-nearest-neighbour
result geometry, which alone suffices to recover values~\citep{kornaropoulos_knn_2019}; oblivious
fetch with query DP (RemoteRAG) closes it. The homomorphic and secret-shared scoring schemes keep
the values themselves encrypted and avoid this class entirely.

\paragraph{Access-pattern hiding.}
The fetch-oriented schemes leak through \emph{access pattern} and \emph{volume}: generic
reconstruction attacks consume access-pattern and communication-volume
leakage~\citep{kellaris2016leakage}, and volume-only attacks defeat schemes that hide \emph{which}
record is touched but not \emph{how many}~\citep{blackstone_revisiting_2020}. These attacks fail
against the oblivious schemes: PIR (Panther, PIR-RAG) genuinely closes the access-pattern channel,
and Compass's ORAM hides which node is touched. The oblivious schemes, not the distance-preserving
ones, are the deployable dense option here (\cref{sec:synthesis}).

\paragraph{Adjacency expansion and graph storage.}
The adjacency and keyword multi-maps leak \emph{volume} (postings-list and one-hop result-set
sizes), so the same volume-only reconstruction applies~\citep{blackstone_revisiting_2020};
volume-hiding EMMs (XorMM, FLASH) bound it by padding, though no padding scheme can asymptotically
beat the naive bound~\citep{ando_cost_2022}, and what remains is the search/query-equality pattern,
closed only by layering ORAM or rotating keys per session. The \emph{node access pattern} and
adjacency-\emph{degree} signatures support re-identification against a public graph in the same
reconstruction family~\citep{kellaris2016leakage}; ORAM (Compass), doubly-oblivious RAM
(H$_2$O$_2$RAM), and 3PC sqrt-ORAM (GORAM) close this channel by hiding which node is touched.

\paragraph{End-to-end KG-RAG.}
Where cryptography is too costly, anonymization (ARoG, PrivGemo) shrinks and pseudonymizes the
structural fingerprint. This is a heuristic obfuscation, not a provable guarantee: it carries
unquantified residual leakage, and the view it does reveal remains exposed to structural
fingerprinting of its subgraph topology.
