The RAG retrieval and storage layer is a confidentiality problem distinct from inference: the
threat is not \emph{what} the server computes but \emph{which} records a query touches and what
the encrypted index reveals at rest, so its primitives are access-hiding and data-hiding rather
than compute-hiding. They compose with the compute-hiding inference layer (\cref{sec:crypto})
but are costed and attacked separately. We organize the layer by the retrieval \emph{functions} that a confidential RAG stack performs in sequence, and report on the schemes that make them confidential.

A standard RAG exercises two of these functions. \emph{Scoring similarity over a stored
index} (\cref{ssec:retr-similarity}) is made confidential either by distance-comparison-preserving
encryption (DCPE), which encrypts the vectors so a standard index still ranks the ciphertext, or
by homomorphic scoring, which keeps the similarity values themselves encrypted. \emph{Hiding which
record a query fetches} (\cref{ssec:retr-access}) is secured by private information retrieval (PIR)
or oblivious RAM (ORAM). A Graph/LightRAG stack~\citep{guo_lightrag} adds three more.
\emph{Constructing the knowledge graph} confidentially (\cref{ssec:retr-kgconstruct}) has no
dedicated primitive: it reduces to confidential inference over the extraction step
(\cref{sec:crypto}--\cref{sec:hybrid}) plus encrypted storage. \emph{Expanding adjacency and
fanning out to source chunks} (\cref{ssec:retr-adjacency}) uses structured and searchable
encryption with encrypted multi-maps (SSE/EMM), layered over ORAM where the access pattern must
hide as well. \emph{Running the whole traversal end-to-end} (\cref{ssec:retr-e2e}) relies on a
trusted execution environment (TEE) or heuristic anonymization. Several schemes serve more than
one function; we place each where its contribution is distinctive and cross-reference the rest.

By the paper's deployment-readiness lens, these schemes are performant in isolation but rarely
self-sufficient: the no-trusted-hardware designs cover retrieval and storage, not generation, and
shift the embedding, reranking, and traversal steps to the client (\cref{sec:synthesis}).

\subsection{Confidential Similarity over a Hidden Index}
\label{ssec:retr-similarity}
Dense retrieval ranks the corpus by similarity to a query embedding. The confidentiality problem for this
function is to compute that ranking without revealing the stored vectors or the query: embeddings
are invertible to text~\citep{vec2text}, so the query embedding discloses the user's question and
the stored vectors the corpus (\cref{tab:retr-perf}). Two families make the similarity computable
over hidden vectors and trade differently between leakage and cost.

\paragraph{Distance comparison preserving encryption (DCPE).}
The most direct approach encrypts each vector with a symmetric transform
($c = s\,e + \lambda$, the same dimension as the plaintext embedding, so the ciphertext imposes
${\approx}1\times$ storage) that preserves distance \emph{comparisons}, so a standard similarity
index ranks the ciphertext at near-plaintext speed with no interaction and no homomorphic
operations (\textbf{CAPRISE} encrypts 2339\,vectors/s). This is the drop-in confidential dense index. The
two schemes differ in \emph{which} comparisons survive. \textbf{SAP}~\citep{fuchsbauer_sap} preserves
\emph{all} pairwise comparisons, including those among database vectors, which leaks the corpus's
relational structure. CAPRISE~\citep{ye_caprise} is \emph{conditional}: it encrypts the stored vectors and the query
under two different procedures, so only query-to-document comparisons survive and the distances
among stored vectors do not. A differential-privacy perturbation of the query blocks inversion,
closing the structural leak SAP leaves open. Either way the cost is exactness and a quantified
comparison leak, examined in \cref{ssec:retr-limits}.

\paragraph{Homomorphic and secret-shared scoring.}
Where any comparison leak is unacceptable, a second family keeps the similarity \emph{values}
themselves encrypted: the server scores the encrypted query against encrypted database vectors so
neither the scores nor their order ever appear in the clear. \textbf{TRSE} pairs two-round searchable
encryption with homomorphic top-$k$ scoring; \textbf{RAGtime-PIANO} layers CKKS scoring over a
lattice-PIR backend; and \textbf{p\textsuperscript{2}RAG} secret-shares the database and the query to two
semi-honest, non-colluding servers that jointly compute the scores. \textbf{RemoteRAG} is two-stage: it first retrieves a
coarse set of $k'$ candidates against a DistanceDP-perturbed embedding (the server sees only the
noised query), then computes \emph{exact} cosine-similarity
top-$k$ over those $k'$ with the true query under partially-homomorphic encryption (PHE), reaching
$0.67$\,s at $100\%$ recall for a small privacy budget. These schemes prune the
candidate set by DP or clustering before scoring, since the cost is the homomorphic arithmetic per
candidate; the benefit is that a single mechanism hides both the query embedding and the at-rest
vectors.

\subsection{Access-Pattern Hiding}
\label{ssec:retr-access}
A scheme can hide the vectors and still leak \emph{which} records a query touches or returns; over
repeated queries this access pattern alone supports database-reconstruction
attacks~\citep{kellaris2016leakage}. The schemes for this function close that channel: the server
returns the matching records without learning which were touched. \textbf{Panther} and \textbf{PIR-RAG} retrieve
through private information retrieval (single- or multi-server, classical or lattice-based), so the
fetch reveals nothing about which record matched. The cost driver is the obliviousness itself:
PIR keeps communication sublinear but forces a server-side linear scan, which is why these run in
seconds at million-scale rather than milliseconds (Panther $18$\,s at $10$M, PIR-RAG $16.8$\,s at
$5$K).

\textbf{Compass} and \textbf{Pacmann} reach the same goal over a graph-based ANN index (HNSW or
NSG): here the ``graph'' is a proximity index over document-chunk embeddings, each vertex a stored
chunk vector rather than a knowledge-graph entity, so both are dense-retrieval schemes hiding the
search over those vectors. Pacmann runs
the iterative ANN traversal on the client and privately fetches each hop's neighborhood by batched
PIR over a public database, retaining $90\%$ of a non-private ANN run's accuracy while
\emph{cutting} latency by $22\%$ at $100$M vectors. Compass wraps an encrypted HNSW index in
client-side Ring-ORAM to defend even a \emph{malicious} server, leaving only the operation type
visible, at $0.57$--$1.28$\,s even over a slow cross-region network. Opal (a TEE design, \cref{ssec:retr-e2e}) reaches the same
access-hiding goal with hardware trust instead of client-side cryptography.

\begin{keyinsight}
At Tier~1 (no trusted hardware), access-pattern hiding is not free; its cost moves to the
client. Compass keeps the ORAM position map and runs a multi-round controller ($\approx$500\,MB of
client state at corpus scale, against a $27$--$75\times$ larger full client-side index), and
Pacmann streams the entire database to preprocess it. The TEE alternative (Opal) hides the same
access pattern with only a key and a counter on the client, but pays for it in a confidential
GPU. The design variable is not whether obliviousness has a cost, but \emph{where} it is paid: on the
client or on trusted hardware.
\end{keyinsight}

\subsection{Confidential Knowledge-Graph Construction}
\label{ssec:retr-kgconstruct}
Graph/LightRAG retrieval presupposes a knowledge graph: an LLM extracts entities and relations
from the corpus into a graph index before any query runs~\citep{guo_lightrag}. Constructing that index on untrusted
infrastructure is the one retrieval function no surveyed scheme makes confidential. It decomposes into two
parts covered elsewhere: the extraction is itself an LLM inference over sensitive text, to which
the inference families of \cref{sec:crypto}--\cref{sec:hybrid} apply, and the resulting graph must
be stored encrypted (\cref{ssec:retr-adjacency}); but no design composes them into an outsourced
confidential construction.

\subsection{Adjacency Expansion and Graph Storage}
\label{ssec:retr-adjacency}
Once the graph exists, LightRAG retrieval matches query keywords to entity and relation nodes (a
dense ANN over entity embeddings, served by the schemes of
\cref{ssec:retr-similarity}--\cref{ssec:retr-access}), then expands one hop to neighboring nodes
and edges and maps each entity to its source chunks. These graph-specific operations leak along
structural channels that dense primitives do not address: the \emph{node access pattern} identifies
the query's subject entity, the \emph{adjacency volume} is a degree signature that re-identifies
nodes against a public graph even under encryption, and the \texttt{source\_id} \emph{fan-out}
links a query to specific source documents.

These channels are closed by general-purpose encrypted-graph-database machinery applied to the RAG
adjacency step. \textbf{XorMM} and \textbf{FLASH} encrypt the adjacency and keyword multi-maps and
pad result-set size so the query-result \emph{volume} does not leak (adjacency and
\texttt{source\_id} fan-out alike), at a storage overhead ranging from ${\approx}1.2$--$2.5\times$
(XorMM) down to near-optimal (FLASH, within a small constant of the volume-hiding lower bound~\citep{ando_cost_2022});
FLASH's conjunctive variant, which answers multi-keyword (AND) queries, additionally reveals which
keyword pairs are queried together, and XorMM's verifiable variant VXorMM detects a malicious
server's forged or incomplete postings via aggregate MACs. \textbf{PeGraph}
combines searchable encryption with secret sharing across two non-colluding servers for ranked
adjacency queries over million-entity graphs in under a second. \textbf{GORAM} is the
heavier-trust 3PC fallback for billion-edge federated graphs ($58$\,ms to $36$\,s per query, with
a one-time index setup under $3$ minutes), and \textbf{H$_2$O$_2$RAM} provides the doubly-oblivious
RAM layer, inside a TEE, on which such a graph store runs. What remains across all of them is
the search/query-equality pattern, not the content, closed only by layering ORAM
(\cref{ssec:retr-access}) or rotating keys per session.

\subsection{End-to-End Confidential KG-RAG}
\label{ssec:retr-e2e}
No surveyed system is a fully confidential graph-RAG pipeline; the purpose-built designs come
closest but rest on trusted hardware or heuristic anonymization, not provable cryptography.
\textbf{Opal} runs the whole pipeline obliviously inside a TEE via Ring-ORAM ($2.32$\,s per query,
$1.57\times$ a non-oblivious run) with no accuracy loss from the obliviousness, but over a metadata-only
identifier graph rather than a content-extracted one, so it is end-to-end confidential by hardware
trust without being graph-RAG in the extraction sense. The graph-RAG systems instead anonymize a
pre-built graph, shielding only what the remote model sees at no cryptographic cost:
\textbf{ARoG}~\citep{ning_arog} maps entity names to machine identifiers so the remote LLM reasons
over de-identified triples, reaching state-of-the-art knowledge-graph question answering (KGQA) at
some utility loss; \textbf{PrivGemo}~\citep{tan_privgemo} adds structural de-uniqueness, a local
``Hand'' shipping the remote ``Brain'' only a pruned, HMAC-pseudonymized subgraph
(${\approx}70\%$ fewer nodes, re-keyed per session). Both keep the raw graph in a trusted local
component and leave confidential construction out of scope, providing \emph{obfuscation} with
unquantified residual leakage rather than a provable guarantee. The deployable options therefore
remain the per-function schemes above.

\subsection{Limitations and Known Attacks}
\label{ssec:retr-limits}

The retrieval schemes trade utility or residual leakage for their speed, and the attacks exploit
that leakage per function. \cref{tab:retr-threat} places every scheme on the security axes of
\cref{sec:threat-axes}, and \cref{tab:retr-attacks} lists the known attacks.

\paragraph{Similarity over a hidden index.}
The distance-comparison-preserving schemes (SAP/DCPE, CAPRISE) preserve distance
\emph{comparisons} between ciphertexts by construction, and that is the leak: property-preserving
encryption is invertible by a distribution-aware adversary~\citep{naveed_ppe_2015}, and the
recovered embeddings read as text via Vec2Text~\citep{vec2text}. SAP also preserves inter-document
comparisons, exposing the corpus's relational structure. CAPRISE defends by making the comparisons
\emph{conditional} (obfuscating inter-document distances) and perturbing the query under differential privacy, cutting Vec2Text
reconstruction from BLEU $83$ to $12$~\citep{ye_caprise} at the cost of a broader retrieval
($k'{\gg}k$) that trades downstream precision. Distance-revealing search also leaks
$k$-nearest-neighbor result geometry, which alone suffices to recover
values~\citep{kornaropoulos_knn_2019} and is closed only by oblivious fetch with query DP
(RemoteRAG). The homomorphic and secret-shared scoring schemes keep the values encrypted and avoid
the class entirely, but are interactive: they return encrypted scores the client must decrypt and
rank, complicating a fully outsourced pipeline.

\paragraph{Access-pattern hiding.}
The fetch-oriented schemes leak through \emph{access pattern} and \emph{volume}: generic
reconstruction attacks exploit access-pattern and communication-volume
leakage~\citep{kellaris2016leakage}, and volume-only attacks defeat schemes that hide \emph{which}
record is touched but not \emph{how many}~\citep{blackstone_revisiting_2020}. The access-pattern
attacks are mitigated using the oblivious schemes: PIR (Panther, PIR-RAG) genuinely closes the
access-pattern channel, and Compass's ORAM hides which node is touched. Volume is a separate
channel: closing it requires making the returned count independent of the query, not merely hiding
which record is touched. A fixed-size PIR fetch and a constant top-$k$ leak no volume by
construction; a variable result set (such as the clusters PIR-RAG returns) must be padded up to a
fixed size, or its candidate budget fixed under the query DP of RemoteRAG and CAPRISE, so every
query exposes the same count.

\paragraph{Adjacency expansion and graph storage.}
The adjacency and keyword multi-maps leak \emph{volume}: the size of a postings list or one-hop
result set. The same volume-only reconstruction applies~\citep{blackstone_revisiting_2020}, and
volume-hiding EMMs (XorMM, FLASH) bound it by padding. What remains is the search/query-equality
pattern, closed only by layering ORAM or rotating keys per session. A node's \emph{access pattern} (which entity a query resolves to) and its adjacency \emph{degree}
(its neighbor count) form a structural fingerprint; matched against a public version of the graph,
that fingerprint re-identifies the encrypted node, the same leakage-abuse reconstruction seen in
the dense case~\citep{kellaris2016leakage}. ORAM (Compass), doubly-oblivious RAM (H$_2$O$_2$RAM),
and 3PC sqrt-ORAM (GORAM) close it by making accesses oblivious: the server no longer sees which
node is touched or how many neighbors it has, so there is no fingerprint to match.

\paragraph{End-to-end KG-RAG.}
The attack here is \emph{structural re-identification}. Anonymizing the view strips entity names
but leaves the graph's topology intact, and a node's neighborhood is often distinctive enough to
act as a fingerprint that re-identifies the entity behind the identifier. Repeated queries sharpen
this fingerprint, because the retriever explores the same node the same way each time, exposing the
same neighbors and partial paths~\citep{tan_privgemo}. \textbf{ARoG} masks only names,
leaving this structural channel open, and its stable identifiers further link a query's subject
across sessions. \textbf{PrivGemo} closes this exact channel: it
clusters the anonymized subgraph into supernodes to blur distinctive neighborhoods, and re-keys the
anonymization per session against cross-session linkage. Both remain heuristic obfuscation rather
than a provable guarantee: the coarsened view still exposes cluster-level connectivity, the
residual leakage is unquantified, and the local component holding the raw graph is fully trusted.
