The RAG retrieval and storage layer is a confidentiality problem distinct from inference:
the threat is not \emph{what} the server computes but \emph{which} records a query touches
and what the encrypted index reveals at rest, so its primitives are access-hiding rather
than compute-hiding. Private information retrieval (PIR) lets a client fetch a record
without the server learning which one; oblivious RAM (ORAM) hides the access pattern of a
sequence of reads and writes; searchable/structured encryption (SSE) and encrypted
multi-maps (EMM) support keyword and adjacency lookups over ciphertext while bounding what
access and volume patterns reveal; and distance-comparison-preserving encryption (DCPE)
keeps similarity search cheap by encrypting vectors so that distance \emph{comparisons}
survive, trading exactness and a quantified leakage for near-plaintext speed. These
primitives compose with the compute-hiding inference layer (\cref{sec:crypto}) but are
costed and attacked separately.

The layer also admits trusted-execution and anonymization designs, so we organize by
retrieval \emph{setting} rather than by mechanism, splitting by index structure, which
determines both cost and leakage: \emph{dense} approximate-nearest-neighbour (ANN) retrieval
over a vector index (naive RAG, \cref{ssec:retr-dense}) and \emph{graph} retrieval and
traversal over a graph-structured index or knowledge graph (Graph/LightRAG,
\cref{ssec:retr-graph}). Storage and retrieval mostly share the same machinery, so we fold
storage into each and flag where they diverge. By the paper's deployment-readiness lens, these
schemes are performant in isolation but rarely self-sufficient: the no-trusted-hardware designs
cover retrieval and storage, not generation, and shift the embedding, re-ranking, and traversal
steps to the client (\cref{sec:synthesis}).

\subsection{Dense Retrieval (Naive RAG)}
\label{ssec:retr-dense}
Dense retrieval ranks the database by similarity to a query embedding. The confidentiality
problem is to perform that ranking without revealing the query, the matches, or the stored
vectors (\cref{tab:retr-perf}). Each is a concrete leakage channel, and two of the three share a root cause:
an embedding is a lossy but invertible encoding of its text, readable by inversion models such
as Vec2Text~\citep{vec2text}, so the \emph{query embedding} discloses the user's
question and the \emph{stored vectors} at rest disclose the corpus. The third channel is
access: \emph{which} database vectors a query touches or returns (the access pattern) reveals
which corpus documents the user is interested in, and over repeated queries this pattern alone
supports database-reconstruction attacks~\citep{kellaris2016leakage}. A scheme
is therefore judged on how many of these three channels (query, access pattern, and at-rest
index) it actually closes (\cref{ssec:retr-limits}).

\paragraph{Oblivious fetch (PIR).}
Panther, PIR-RAG, p\textsuperscript{2}RAG, and RAGtime-PIANO retrieve through PIR (single- or
multi-server, classical or lattice/CKKS-based), so the server returns the matching vectors
without learning which were touched, closing the access-pattern channel. The cost driver is
the obliviousness itself: PIR keeps communication sublinear but forces a server-side linear
scan, which is why these run in seconds at million-scale rather than milliseconds.

\paragraph{Homomorphic scoring.}
A distinct subclass keeps the similarity \emph{scoring} under encryption rather than hiding
the fetch: the server scores the encrypted query against encrypted database vectors
homomorphically, so the similarity values and their order never appear in the clear. TRSE
pairs two-round searchable encryption with homomorphic top-$k$ scoring, and RAGtime-PIANO
layers CKKS scoring over its lattice PIR. RemoteRAG is two-stage: it first coarse-retrieves
$k'$ candidates against a DistanceDP-perturbed embedding (the cloud sees only the noised
query), then computes \emph{exact} cosine-similarity top-$k$ over those $k'$ with the true
query under partially-homomorphic encryption (PHE). The user decrypts the returned distances
and sorts them locally, with optional $k$-out-of-$k'$ oblivious transfer for the final fetch.
The scheme reaches $0.67$\,s at $100\%$ recall for a small privacy budget. The shared cost is the
homomorphic arithmetic per candidate, so these schemes prune the candidate set (DP,
clustering) before scoring; the shared benefit is that one CKKS/PHE machinery protects both
the query embedding and the at-rest vectors.

\paragraph{Distance-comparison-preserving encryption (DCPE).}
SAP/DCPE and CAPRISE make the opposite trade-off: a symmetric per-vector transform
($c = s\,e + \lambda$, the same dimension as the plaintext embedding, so the ciphertext
imposes ${\approx}1\times$ storage)
that preserves \emph{distance comparisons}, letting the server rank encrypted database
vectors by similarity to an encrypted query at near-plaintext speed (CAPRISE encrypts
2339\,vectors/s) with no interaction and no homomorphic operations. The two differ in
\emph{which} comparisons survive. SAP~\citep{fuchsbauer_sap} preserves \emph{all} pairwise
comparisons, including those among database vectors, which leaks the corpus's relational
structure to a vector-analysis attack. CAPRISE~\citep{ye_caprise} is \emph{conditional}: by
adding asymmetric noise to query versus database encryptions it preserves only
query-to-document comparisons while obfuscating inter-document ones, and perturbs the query
under differential privacy, closing the structural leak SAP leaves open. The shared price is
exactness and a quantified leakage, examined in \cref{ssec:retr-limits}.

\subsection{Graph Retrieval and Traversal (Graph/LightRAG)}
\label{ssec:retr-graph}
Graph-RAG retrieves over a graph-structured index or knowledge graph: entity/relation ANN
lookups, one-hop adjacency expansion, and \texttt{source\_id} fan-out (the LightRAG
surface~\citep{guo_lightrag}). These ops leak differently from dense search, along three
graph-specific channels. First, the \emph{node access pattern} (which entity or relation a
query resolves to) identifies the subject of the query directly (an adjacency lookup on
``Alice'' reveals interest in Alice even if the edge contents stay encrypted). Second, the
\emph{adjacency volume} (how many neighbours a one-hop expansion returns) leaks each node's
degree, and a degree sequence is a structural fingerprint that re-identifies nodes against a
public graph even under encryption. Third, the \texttt{source\_id} \emph{fan-out} (which
chunks an entity maps to) links a query to specific source documents. Because these surfaces
are about \emph{structure and access}, not arithmetic, dense-retrieval primitives do not
address them and graph retrieval needs different machinery (\cref{tab:retr-perf}).

\paragraph{Graph-ANN over an oblivious index.}
Pacmann and Compass serve the entity/relation ANN lookups that open a LightRAG-style
retrieval, hiding which node a query resolves to: Pacmann via client-side batched PIR over a
public graph, Compass by wrapping an encrypted HNSW index in client-side ORAM to defend even
a \emph{malicious} server (leaving only the operation type visible). The TEE baseline Opal
(\cref{sec:tee}) reaches the same access-hiding goal with hardware trust rather than
client-side cryptography. These run in sub-second to seconds at million-node scale, but the
obliviousness places the cost on the client: Compass runs the ORAM controller and
holds its position map, and Pacmann performs the traversal client-side. This is a deployment
cost the ``no trusted hardware'' label hides and that we score as client-reliance in
\cref{sec:synthesis}.

\begin{keyinsight}
At Tier~1 (no trusted hardware), access-pattern hiding is not free; its cost moves to the
client. Compass keeps the ORAM position map and runs a multi-round controller ($\approx$500\,MB of
client state at corpus scale, against a $27$--$75\times$ larger full client-side index), and
Pacmann streams the entire database to preprocess it. The TEE alternative (Opal) hides the same
access pattern with only a key and a counter on the client, but pays for it in a confidential
GPU. The design variable is not whether obliviousness costs, but \emph{where} it is paid: on the
client or on trusted hardware.
\end{keyinsight}

\paragraph{Volume-hiding adjacency.}
XorMM, FLASH, and PeGraph encrypt the adjacency and keyword multi-maps that graph retrieval
traverses, returning postings while padding result-set size so the query-result \emph{volume}
does not leak. This closes the adjacency-volume and \texttt{source\_id} fan-out channels
above, at a storage overhead ranging from near-optimal (FLASH, within a small constant of the
volume-hiding lower bound) to ${\approx}1.2$--$2.5\times$ (XorMM); the conjunctive variant FLASH
adds a keyword-pair access pattern of its own. All three target an honest-but-curious server;
XorMM additionally admits a verifiable variant, VXorMM, that detects a malicious server
returning forged or incomplete postings by authenticating the response with aggregate MACs, at
twice the storage and a verification cost linear in the returned volume. What remains is the
search/query-equality pattern, not the content, closed only by layering ORAM (as Compass
does) or rotating keys per session. H$_2$O$_2$RAM supplies a doubly-oblivious RAM substrate
(inside a TEE) beneath such a graph store, and GORAM is the heavier-trust 3PC fallback for
billion-edge federated graphs.

\paragraph{Anonymization.}
Where exact cryptography is too costly, PrivGemo~\citep{tan_privgemo} attacks the graph leakage
channels directly. A local ``Hand'' module explores the graph and hands the remote ``Brain''
LLM only a sanitized view of the retrieved subgraph: structure pruning and clustering strip
motifs weakly connected to the query anchors, removing the uniquely-identifying topology that
the adjacency-volume and degree-signature channels above would leak (${\approx}70\%$ node
reduction, e.g.\ a ${>}2.4$M-node ComplexWebQuestions (CWQ) subgraph to ${\approx}732$K). Entity labels are replaced
by HMAC session identifiers, so the Brain reasons over de-identified nodes, and the dual-tower
split keeps the raw graph local. This secures graph-view retrieval at no cryptographic cost,
but is quality-preserving \emph{obfuscation}, not a provable-confidentiality guarantee, with
unquantified residual leakage (the hybrid/anonymization lineage of \cref{sec:hybrid}).

\paragraph{} Together these cover LightRAG's retrieval surface: entity/relation/chunk ANN (Compass, Pacmann, CAPRISE), one-hop adjacency expansion (XorMM, FLASH), and graph storage (PeGraph, GORAM). This breadth is why the confidential-RAG frontier lies at the retrieval layer rather than at crypto inference
(\cref{sec:synthesis}).

\subsection{Limitations and Known Attacks}
\label{ssec:retr-limits}

The retrieval schemes trade exactness or residual leakage for their speed, and the leakage
profile differs by index structure: dense and graph retrieval are attacked through different
channels, so we treat them separately. \cref{tab:retr-threat} places every scheme on the
security axes of \cref{sec:threat-axes}, and \cref{tab:retr-attacks} lists the known attacks.

\paragraph{Dense retrieval.}
The distance-comparison-preserving schemes (SAP/DCPE, CAPRISE) preserve distance
\emph{comparisons} on ciphertext by construction. That is precisely the leak. The
property-preserving-encryption family is invertible from ciphertext plus an auxiliary data
distribution~\citep{naveed_ppe_2015}, and the embeddings recovered this way are readable as
text by inversion models such as Vec2Text~\citep{vec2text}; SAP additionally
preserves inter-document comparisons, exposing the corpus's relational structure. CAPRISE is
the co-designed defence: it makes the comparisons \emph{conditional} (obfuscating
inter-document distances) and perturbs the query under differential privacy. The
fetch-oriented schemes leak instead through \emph{access pattern} and \emph{volume}: generic
reconstruction attacks consume access-pattern and communication-volume
leakage~\citep{kellaris2016leakage}, $k$-nearest-neighbour query leakage alone suffices to
recover values~\citep{kornaropoulos_knn_2019}, and volume-only attacks defeat schemes that
hide \emph{which} record is touched but not \emph{how many}~\citep{blackstone_revisiting_2020}.
These attacks fail against the oblivious schemes: PIR (Panther, PIR-RAG, p\textsuperscript{2}RAG)
genuinely closes the access-pattern channel, and homomorphic scoring (TRSE, RemoteRAG) keeps
the similarity values themselves encrypted. The oblivious schemes, not the
distance-preserving ones, are the deployable schemes here (\cref{sec:synthesis}).

\paragraph{Graph retrieval.}
Graph retrieval is attacked along the structural channels of \cref{ssec:retr-graph}. The
adjacency and keyword multi-maps leak \emph{volume} (postings-list and one-hop result-set
sizes), so the same volume-only reconstruction applies~\citep{blackstone_revisiting_2020};
volume-hiding EMMs (XorMM, FLASH) bound it by padding, though no padding scheme can
asymptotically beat the naive bound~\citep{ando_cost_2022}, and what remains is the
search/query-equality pattern, closed only by layering ORAM or rotating keys per session.
The \emph{node access pattern} and adjacency-\emph{degree} signatures support
re-identification against a public graph in the same reconstruction
family~\citep{kellaris2016leakage}; ORAM (Compass) and doubly-oblivious RAM (H$_2$O$_2$RAM)
close this channel by hiding which node is touched, while GORAM's 3PC sqrt-ORAM does so for
billion-edge federated graphs. Where cryptography is too costly, anonymization (PrivGemo)
instead shrinks and pseudonymizes the structural fingerprint. This is a heuristic obfuscation,
not a provable guarantee, with unquantified residual leakage.
